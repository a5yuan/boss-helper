# 夜间复盘提示词

每天夜里运行一次。分两步：先**复盘**（把当天所有 commit 过一遍，产出写进 `LESSONS.md`），再**整理**（合并重复、标记失效、归档陈旧）。

只做第一步的错题本会膨胀到没人读——规律被埋住，旧笔记还在自信地用错。整理和记录同等重要。

## 输入

- 当天所有 commit（含 message、diff、关联 issue/PR）
- 当天所有 release / tag
- 当前 `LESSONS.md` 全文（用于判断是否已有同类教训）

## 审查的三个视角

### 1. 哪些修复之后又返工了

找：当天修的，是当天或前一天刚发布的改动。

判断标准：

- 同一个文件/函数在 24-48 小时内被反复修改
- 某个 issue 被 reopen，或修复后出现同类的新的 issue
- 同一类改动在不同位置重复出现（说明上一轮没覆盖全部入口）

### 2. 哪些压根不该合并

判断标准：

- 改动引入的问题比它解决的问题更严重
- 范围超出 issue 描述，夹带了无关重构
- 没有测试，或测试只验证实现细节
- 绕过了标准流程（例如直接改主干、跳过 review）

### 3. 哪些验证做得太糙

判断标准：

- 声称"已修复"但无法复现报告者的场景
- 测试通过但行为仍然错误（测试没有真正覆盖）
- 只在单一环境/单一入口验证
- 把"我本地跑通了"当作验证完成

## 输出格式

对每一个发现，写一条：

```markdown
### <一句话规则，祈使句>

<为什么。违反它的代价。>

<证据：commit sha / issue 号>

Seen N× (YYYY-MM-DD, ...)
```

## 合并规则

写入前先检查 `LESSONS.md` 是否已有同类教训：

- **已有**：不新增条目。把今天的日期加到该条的 `Seen` 列表里，计数 +1。
- **没有**：新增一条，`Seen 1×`，附今天日期。
- **某条 `Seen` 达到 3 个不同日期**：把规则句晋升到 `docs/code-standards.md`，在晋升记录表里登记，然后从 `LESSONS.md` 删除该条。

## 硬性约束

- 没有 commit / issue 号作证据的，不写。凭印象的教训不可追溯，会变成噪音。
- 规则用祈使句，一句话。写不成一句话，说明还没想清楚。
- 同一天同一个问题出现多次，`Seen` 只记 1 次。计数按日期算。
- 宁可少写。错题本的价值在密度，不在长度。
- 如果某天没有值得记录的，就什么都不写。不要为了凑数而编。

---

# 第二步：整理

复盘写完后，对 `LESSONS.md` 全文做一遍整理。**这一步只做减法，不新增条目。**

## 4. 合并语义重复

两条教训如果指向同一个行为要求，合并成一条：

- 保留描述更准确的那句规则
- `Seen` 日期列表取并集，重新计算 `N×`
- 证据取并集，去重
- 合并后的条目放在原位置靠前的那条，另一条删除

判断"语义重复"的标准：**如果 agent 遵守了 A，是否必然也遵守 B？** 是，就合并。

不要合并"相关"的教训。相关 ≠ 重复。

## 5. 标记失效

某条教训如果已经不成立了，标记而不是直接删：

```markdown
~~### <原规则>~~

**已失效（YYYY-MM-DD）**：<为什么不再适用——代码已重构 / 该依赖已移除 / 相关模块已下线>

<保留原证据，供追溯>

Seen N× (...)
```

保留原文是为了让后来者能判断"这条当初为什么存在"。**失效不等于错误**，可能只是环境变了。

只有在满足下面任一条时才直接删除：

- 该规则已晋升到 `docs/code-standards.md`（正常晋升流程）
- 该规则本身就是错的（当初记错了），删除时在复盘记录表备注

## 6. 归档陈旧

`Seen 1×` 且距今超过 90 天、期间再未命中的条目，移到 `LESSONS.md` 末尾的「归档」折叠区：

```markdown
## 归档

<details>
<summary>2026-Q4 归档（N 条）</summary>

### <规则>
<原因>
<证据>
Seen 1× (YYYY-MM-DD)

</details>
```

归档区不参与日常阅读，但保留可追溯性。**不要物理删除**——它可能只是因为最近没有相关改动，而不是真的没用。

## 整理的硬性约束

- **只删不加。** 整理步骤不允许新增教训，新增只发生在第一步。
- **每次整理最多动 5 条。** 大改会让 `LESSONS.md` 的 diff 无法审查，人也就不会看了。
- **合并和归档都要在复盘记录表备注。** 写清动了哪几条、为什么。
- **拿不准的就不动。** 整理的目标是可读性，不是极简。一条看起来冗余但判断不清的条目，留着比删错好。

## 整理的触发条件

不是每天都整理。满足任一条件才跑第二步：

- `LESSONS.md` 超过 150 行
- 距上次整理超过 30 天
- 本次复盘新增了 ≥3 条教训

否则跳过，只做第一步。频繁整理本身就是噪音。

---

## 复盘记录表

在 `LESSONS.md` 底部的表格里追加一行：日期、commit 数、release 数、返工数、新增教训数。

返工比例 = 返工数 / commit 数。连续多天超过 15%，说明验证环节有系统性问题，需要单独提出，而不是继续记单条教训。

跑过整理的日子，在备注列写 `整理：合并 N / 失效 N / 归档 N`。
